**Goal:** Create or update one project-owned Project Development Guide from repository evidence and one team decision gate.

**Scope:** This optional setup task adapts the imported Agile Project Development Guide into a project-owned SpecX document for future work. It may be run again when the repository or team direction changes. It must not edit repository files, alter imported resources, require every section to be approved, start another pipeline, or claim that existing code already complies.

**Verification / Definition of Done:**
- [ ] The imported guide was read by slug, the project guide template supplied document shape, and only selected applicable concern bodies were read and proposed.
- [ ] Repository languages, manifests, structure, tests, styling, data tools, and existing decisions were inspected before asking for a choice.
- [ ] Each proposed section distinguished observed practice from its forward-looking target and retained the guide's stable section and Adoption keys under the fixed Standards section.
- [ ] An existing project-owned guide was selected by durable id or exact title and kept in its current folder; imported resources were never update targets.
- [ ] A new guide destination was outside every protected imported collection, with one advisory if an invalid override was skipped.
- [ ] One preview showed material changes, proposed Draft or Approved status per applicable section, unresolved choices, and the exact create or update destination.
- [ ] Newly approved or revised sections had the person's acceptance; existing Approved sections stayed intact, unresolved new sections stayed Draft, and a deferred revision did not replace an earlier Approved decision.
- [ ] The write was idempotent by durable id or exact title, preserved unrelated existing sections, and never created a duplicate for the same project.
- [ ] No repository file changed, no other pipeline started, and the handoff named the guide, statuses, evidence, and next action.

**Instructions:**

1. Expose concise state: `inspecting`, `waiting` for the one decision gate, `writing`, or `blocked` when a required SpecX workspace or source is unavailable. Use `done`, `needs_input`, or `blocked` with a one-line reason; never call an unobserved write done.
2. Resolve the imported Agile Project Development Guide by slug `agile-sdlc-project-development-guide`. Read its keyed Purpose and Adoption section, including its compact applicability index; do not read the Standards container body to select concerns. Resolve Agile Project Development Guide Template by exact title (slug `agile-sdlc-project-development-guide-template`) for concern titles and output shape. If either source or the SpecX document workspace is unavailable, stop `blocked` and name it. Treat the imported guide as read-only; its Draft status is a proposed future direction, not evidence that the repository complies.
3. Inspect the target repository before asking: languages and manifests, relevant directories and boundaries, UI and styling approach, state/data access, APIs, persistence and migrations, existing test commands, and any explicit project decisions. Select only applicable concern keys, including Code Structure and Tests and Routine Checks where the repository supports them, then read only those keyed concern bodies and their Adoption subsections. Do not read an omitted concern body or the Standards parent as a substitute. Do not invent a framework, dependency, product rule, missing test, or deployment requirement. For each selected section, note the observed practice, the smallest useful target, a material gap or exception, and whether the target can be accepted now or should remain Draft. A brownfield gap is an adoption note, not a demand to refactor unrelated code.
4. Resolve an explicitly supplied project-guide document id first; otherwise use an exact-title document lookup for `Project Development Guide`. Exclude imported-resource artifacts using collection metadata and folder ancestry, never a folder name. If several project-owned exact matches remain, defer identity selection to the single preview; never silently create another. For one existing guide, read its current folder property and preserve its id, folder, stable section keys, and unrelated sections. Never relocate it. For a new guide, use a valid create-only folder override or ensure `Project Work/Standards`, checking that the chosen destination is outside protected imported ancestry; skip a protected override for that default with one advisory. Treat `folderId` as create authority and `folderPath` as informational. Never list folder contents.
5. Compare each applicable imported section with the selected project guide, if any. Preserve an unchanged Approved project section as the current convention. For a proposed revision, show the old Approved decision and the proposed replacement; the old decision remains governing until that replacement is accepted. Leave a deferred proposal unwritten so it cannot replace the Approved text. Omit irrelevant imported sections from a new project guide; preserve unrelated existing project sections on update. Keep each selected section's `Status` and `Applies to` fields under its keyed Adoption subsection. Put concise repository evidence, target rationale, and any gradual adoption note in that section without claiming present compliance.
6. Present one concise preview before writing: target guide identity and folder, repository profile and evidence, applicable section keys with proposed Draft or Approved status, material current-to-target differences or deferred revisions, and any consequential choice or placement advisory. Ask once for acceptance of the proposed statuses and changes, allowing the person to accept a subset or revise a consequential target in that same gate. No section becomes Approved solely from repository observation. If the person cancels, finish `done` with reason `cancelled; guide unchanged`. If one consequential choice remains unresolved, leave that section Draft and continue with accepted independent sections; use `needs_input` only when no useful independent guide can be written.
7. After acceptance, create or update exactly one project-owned SpecX document titled `Project Development Guide`. For a create, instantiate Agile Project Development Guide Template in the resolved destination, use the imported guide as the proposed content, and include only selected applicable sections with their stable keys and keyed Adoption subsections. Adapt Purpose and Adoption to this repository, including a compact index of included concern keys and applicability. Render the title as H1, Purpose and Adoption and Standards as H2 siblings, included concerns as H3 under Standards, and their Adoption subsections as H4; retain the heading keys. For an update, write by durable id in its current folder, preserving unrelated sections and prior Approved text for every deferred revision. Mark an accepted future target Approved even when older code has a recorded gap; leave unsupported or unaccepted new targets Draft. Do not make a second approval request, mutate the imported guide, or edit the repository. If the exact target already matches the accepted result, finish as a truthful no-op without writing a duplicate.
8. Hand off in at most five lines: Outcome, Decision, Artifact, Evidence, and Next action. Name the exact project-guide id or title, informational folder, Approved and Draft sections, material gaps, and any unresolved decision. State that future Agile work may use the relevant sections; do not start it.
