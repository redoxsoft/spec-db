**Goal:** Inspect the source and repository, persist a resumable technical-design drafting contract, and obtain one approval.

**Scope:** This task accepts engineering notes, a feature spec, a PRD, or a tech-debt description, infers the subject and the title `<Subject> - Agile Tech Spec`, and inspects the workspace enough to ground that choice. It must not draft the document body, modify source code, or start another pipeline.

**Verification / Definition of Done:**
- [ ] Unformatted input was accepted.
- [ ] The source and relevant repository evidence were inspected before any question.
- [ ] Source reference, subject, title, Technical Design mode, applicable modules, assumptions, and decisions were established.
- [ ] Applicable project-guide sections were resolved when they informed a technical choice, with a concise chosen direction carried to drafting.
- [ ] Provenance was recorded only for material decisions and assumptions.
- [ ] Artifact identity, governing feature/source identity, a title collision, and any placement advisory were resolved in the same approval preview without listing folder contents.
- [ ] An existing Tech Spec keeps its exact current folder; a new one uses a valid create-only override, an explicitly supplied valid governing feature/source folder outside the protected import tree, or `Project Work/Work/<Subject>` with an advisory.
- [ ] One preview showed only applicable provenance classes and did not force empty categories.
- [ ] The named Persisted handoff stores the exact artifact and governing-source references, canonical `folderId`, informational `folderPath`, and every other field needed by a fresh drafting context.
- [ ] Agile Technical Design Template (`agile-sdlc-technical-design-template`) was present, or the task stopped with workspace setup required and named that title and slug.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including an explicitly supplied primary Feature Spec or other governing feature-level source and a destination-folder override. Establish a durable source reference: an artifact id, exact document title, ticket, commit, or supplied-input description. Do not infer that every source is a placement anchor.
3. Inspect the source and relevant repository language, manifests, directory shape, tests, interfaces, data tools, and existing design decisions before asking. Infer a concise subject and `<Subject> - Agile Tech Spec`; preserve upstream behaviors and acceptance criteria only when evidenced. For a technical concern the design will address, resolve a supplied project-guide id first or use an exact-title lookup for `Project Development Guide` outside imported-collection ancestry; if none exists, use imported `agile-sdlc-project-development-guide`. If several project-owned guides match, include identity selection in the existing approval gate. Read only applicable sections and Status fields. Approved project sections govern; Draft sections provide a forward-looking default to weigh against the repository. Record a concise target or material exception, not a requirement to clean up unrelated code. If no guide is available, use repository evidence and advise once; Draft alone creates no new gate.
4. Determine which optional modules are relevant: API or interfaces, data, migration, security, operations, rollout, and rollback. Resolve the produced artifact's identity without browsing folders: use a supplied artifact id first, otherwise exact-title or explicit-reference lookup. For one match, read its cheap folder property and preserve its exact current `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location; defaults and overrides never move it. Ignore a supplied override on this update and include a concise advisory. If several exact matches exist, include one identity selection in the approval gate.
5. For a new Tech Spec, resolve placement once in this order: a valid explicit override; the folder property of the explicitly supplied primary Feature Spec or other governing feature-level source when its identity resolves and its folder is outside the protected imported collection; otherwise ensure and use `Project Work/Work/<Subject>`, applying only host-required sanitization, and record a concise standalone-placement advisory. Resolve the governing source by supplied artifact id first or exact title/reference otherwise; never use a PRD or incidental source as a feature anchor. If an override is protected, ignore it and continue to source inheritance or the default with one advisory. If the governing source is protected, use the standalone default with one advisory. Determine protection from imported-resource metadata and hierarchy ancestry, never a folder name.
6. Fetch hierarchy only to check ancestry or ensure the known fallback path; never list folder contents to find artifacts, detect collisions, or choose placement. Treat `folderId` as write authority and `folderPath` as informational. Do not assume workspace configuration or create a placement enum. If an exact artifact or governing-source lookup has several matches, resolve that identity in the single approval gate rather than disambiguating by folder.
7. Check Agile Technical Design Template availability; report `blocked` and name it when unavailable. Give provenance `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions.
8. Present one preview of at most six lines covering source and governing anchor, subject/title and mode, intended boundaries/modules, exact update or create destination, applicable material decisions or assumptions including a guide exception when relevant, any collision or placement advisory, and next action. Omit inapplicable details. Set state to `waiting` and ask once for acknowledgement.
9. After acknowledgement, **Persisted handoff:** store status `approved`, source reference, exact governing-source id/reference when supplied, subject, produced title, approved mode, applicable modules, exact output artifact id/reference when one exists, collision and create/update disposition, canonical `folderId`, informational `folderPath`, any concise placement advisory, material assumptions and decisions with provenance, and concise guide basis when used: exact guide id/reference, section keys and statuses, and chosen targets or exceptions. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state.
10. Do not draft the document body or modify source code.
