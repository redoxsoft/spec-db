**Goal:** Inspect the source and repository, persist a resumable feature-spec drafting contract, and obtain one approval.

**Scope:** This task accepts unformatted notes, a ticket, a user story, or a product-spec excerpt; grounds it in available source and repository evidence; and confirms Feature mode, title, and any proposed split. It must not draft the document body, modify source code, or create another artifact.

**Verification / Definition of Done:**
- [ ] Unformatted input was accepted.
- [ ] The source and relevant repository evidence were inspected before any question.
- [ ] Source reference, subject, produced title, approved mode, and material assumptions and decisions were established.
- [ ] Provenance was recorded only for material decisions and assumptions.
- [ ] Artifact identity, a title collision, any proposed split, and any placement advisory were resolved in the same approval preview without listing folder contents.
- [ ] Existing artifacts keep their exact current folders; each new accepted feature uses its own `Project Work/Features/<approved subject>` folder unless that artifact has a valid create-only override.
- [ ] One preview showed only applicable provenance classes and did not force empty categories.
- [ ] The named Persisted handoff stores each exact artifact reference, canonical `folderId`, informational `folderPath`, and every other field needed by a fresh drafting context.
- [ ] Agile Product Spec Template (`agile-sdlc-product-spec-template`) was present, or the task stopped with workspace setup required and named that title and slug.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including a destination-folder override explicitly assigned to a new output, and establish a durable source reference: an exact document title, ticket, commit, or supplied-input description. Inspect the source and relevant repository files, manifests, tests, and existing specifications before asking.
3. Infer a concise subject and `<Subject> - Agile Feature Spec`. Read "Agile Artifact Routing Guide" only when deciding whether Product Spec Feature mode resolves actual behavioral uncertainty or whether the default Work Item route is sufficient.
4. If the brief bundles independently deliverable capabilities, propose subjects and boundaries only when separate documents would clarify the work. Preserve the unsplit brief unless the proposal is approved. Do not silently impose a split.
5. Resolve each produced artifact's identity without browsing folders: use a supplied artifact id first, otherwise exact-title or explicit-reference lookup. For one match, read its cheap folder property and preserve its exact current `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location; defaults and overrides never move it. Ignore an override assigned to this existing artifact and include a concise advisory. If several exact matches exist, include one identity selection in the approval gate. Do not use folder-content listing to find or disambiguate artifacts.
6. Resolve placement once for each new accepted Feature Spec. Use a valid override explicitly assigned to that artifact; otherwise ensure and use `Project Work/Features/<approved subject>`, applying only host-required sanitization to the approved subject. A PRD or other source folder is not inherited. Each split feature gets a separate subject folder; a general override is not silently shared across split outputs. Determine protected imported-collection ancestry from imported-resource metadata and the folder hierarchy, never a folder name. Reject a protected-tree override and use that feature's default with one concise advisory. Fetch hierarchy only to check ancestry or ensure a known path; never list folder contents. Treat `folderId` as write authority and `folderPath` as informational. Do not assume workspace configuration or create a placement enum.
7. Check Agile Product Spec Template availability. If it is unavailable, report `blocked` and name it. Give provenance `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions.
8. Present one preview of at most six lines covering source, accepted subject/title and mode or split, intended scope, each exact update or create destination, applicable material decisions or assumptions with provenance, any collision or placement advisory, and next action. Omit inapplicable details. Set state to `waiting` and ask once for acknowledgement.
9. After acknowledgement, **Persisted handoff:** store status `approved`, source reference, each accepted subject and produced title, approved mode, split disposition, each exact artifact id/reference when one exists, collision and create/update disposition, canonical `folderId`, informational `folderPath`, any concise placement advisory, and material assumptions and decisions with provenance. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state. If the user chooses the default Work Item route, finish without approval and state that next action.
10. Do not draft the document body or modify source code.
