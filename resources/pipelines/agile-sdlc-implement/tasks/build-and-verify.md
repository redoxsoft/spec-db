**Goal:** Implement and verify the approved execution contract within its repository boundary, then persist one truthful implementation result for a fresh recording task.

**Scope:** This task loads the approved durable Work Item or compact fast-path contract, implements within its permitted boundary, performs its automated or manual verification approach, and stores a concise structured implementation result in SpecX run context. It must not expand the outcome or boundary, change what an acceptance criterion asserts, weaken verification, push, tag, or merge, paste raw logs into durable state, or continue when this run is not approved.

**Verification / Definition of Done:**
- [ ] The complete Task 1 Persisted handoff was loaded, and exact missing fields were named before stopping blocked.
- [ ] The selected Work Item was reread by exact title, or the complete compact fast-path contract was used without requiring a Work Item or document workspace.
- [ ] Implementation and any required test coverage stayed within the permitted boundary.
- [ ] The recorded automated commands were run and/or the recorded concrete manual observations were performed; an explicit not-applicable reason was preserved where relevant.
- [ ] Each acceptance criterion was evaluated against observed evidence without inventing a pass.
- [ ] A consequential decision discovered on the fast path caused intake to be rerun in durable mode; in durable mode it was persisted in the Work Item before needs_input, and a later supplied resolution and its provenance were persisted there before execution resumed.
- [ ] The reported outcome is exactly done, failed, needs_input, or blocked, with a one-line reason using the defined meaning.
- [ ] SpecX run context contains a concise structured implementation result with outcome and reason, request/Work Item reference, and every field actually established: changed areas and files, acceptance results, limitations or next action, Target Revision manifest and revision id, target branch, and one repeatable entry for every actual command or manual observation. An early blocked or needs_input result before checks may omit repository identity and events.
- [ ] Each verification entry preserves date, command or action, result, exit code and counts or concise observation, acceptance-criterion references, verification requirement, limitations, and an artifact pointer when one exists, without raw logs.
- [ ] An initial failed check and a later passing check were both preserved when a relevant code or environment repair occurred between them.

**Instructions:**

1. Expose concise state while working: `implementing` while editing, `verifying` while checking acceptance criteria, `waiting` for a newly discovered consequential decision, or `blocked` when required work cannot run.
2. Reload the Task 1 **Persisted handoff**: status, exact subject, contract mode, and either exact Work Item title or the compact contract's originating request/reference, exact subject, outcome, criteria, exact permitted paths, verification, and approved status. Name every missing field and stop `blocked`; stop unless status is approved. Do not reconstruct state from conversation or re-ask an approved choice.
3. For `durable-work-item`, reread the Work Item by its exact stored title and use it as authority for outcome, criteria, boundary, verification, and optional material content. For `trivial-fast-path`, use the loaded compact contract directly and do not require a Work Item, template, or document workspace.
4. Inspect the relevant current files before editing. Implement the intended outcome inside the permitted boundary, following repository-observed conventions and accepted agent-inferred defaults. Add or adjust tests when necessary to evaluate an acceptance criterion. If fast-path work proves nontrivial, risky, ambiguous, or outside its exact paths, stop rather than stretching the compact contract; rerun intake in durable Work Item mode. If durable-mode implementation discovers a new consequential choice, update the Work Item before stopping: preserve the decision, alternatives, evidenced recommendation, what cannot safely proceed, and provenance `unresolved`. Persist `needs_input` with that durable decision reference. On a rerun, preserve a supplied resolution before resuming and do not ask it again.
5. Read Agile Test Strategy Guide only when the selected contract and repository do not already establish the coverage needed to evaluate an acceptance criterion. Technical constraints must come from the selected contract, repository evidence, or a governing design; do not load another knowledge spec.
6. Perform the selected contract's verification approach. Run each recorded automated command and capture its exit code and useful test counts. Perform each recorded manual check as a concrete action and capture the observed result. Preserve an explicit not-applicable reason without inventing a replacement command or a pass. For every actual check or observation, add a repeatable verification entry to the implementation result with: date; exact command or concrete action; result; exit code and useful counts, or concise observation; acceptance-criterion references; verification requirement; limitations; and an artifact pointer when one exists. Keep raw logs out of run context.

Fix freely inside the permitted boundary. Stop and report instead of continuing when the fix would touch an area outside that boundary, change what an acceptance criterion asserts, or make a check pass by weakening, skipping, deleting, or mocking past the thing under test. Stop and report when the failure existed before this change. Do not re-run an unchanged command against unchanged code and environment hoping for a different result; after a relevant code or environment repair, rerunning the affected command is required verification.

7. Diagnose and repair failures caused by this change while the repair stays inside the boundary and preserves the outcome, criteria, and verification integrity. Continue or stop based on those conditions, never on a tally. Leave incomplete work in place when the next safe action crosses the boundary. When a repair is followed by a passing rerun, retain both the initial failed entry and the later passing entry; the passing entry may identify the failed entry it resolves.
8. While editing and staging, hold these invariants: no drive-by refactoring or formatting churn outside the permitted boundary; stage by explicit path and never `git add .` or `git add -A`; never `git push`, tag, or merge; never claim a pass without an observed command result or concrete manual observation.
9. Evaluate every acceptance criterion against observed behavior. A skipped required check is not a pass. Preserve pre-existing or unrelated failures as limitations rather than repairing them outside scope.
10. Determine exactly one outcome and a one-line reason: `done` means required verification passed or was concretely observed; `failed` means verification ran and found a defect or unmet acceptance criterion; `needs_input` means one unresolved consequential decision requires a person; `blocked` means the environment or authority is unavailable, or required durable state is unavailable.
11. After repository state has been established, create one Target Revision manifest with a new stable revision id and full base commit SHA. A clean revision has no boundary entries and represents that exact commit. For a dirty revision, the base SHA is ancestry context; add entries sorted by repository-relative path for every path changed or untracked inside the permitted boundary relative to that base: path plus SHA-256 of current regular-file bytes, SHA-256 of symlink target bytes, `gitlink:<commit>` for a submodule, or `MISSING`. Include the permitted-boundary description whenever later recovery cannot rely on a durable Work Item; a fast-path manifest always retains its exact permitted paths. Ensure no changed path inside that boundary is absent. Do not compute an aggregate hash or auto-commit. An early blocked or needs_input outcome before repository identity is available has no manifest.
12. Before completing, persist one structured implementation result containing outcome and one-line reason; contract mode and originating request or exact Work Item title; every changed area, exact file, per-criterion result, limitation, next action, target branch, and durable decision reference actually established; the Target Revision manifest and revision id when created; and the ordered verification entries from steps 6 and 7. Each actual entry references that revision id and the manifest is not repeated. An early blocked or needs_input outcome before checks may contain neither manifest nor entries; do not invent either. Persist actual failed, passed, blocked, and not-applicable history without collapsing it. This is the complete build-to-record handoff for a fresh Task 3 and must not depend on conversation.
