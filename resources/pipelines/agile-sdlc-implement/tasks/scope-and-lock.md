**Goal:** Establish the smallest complete execution contract from inspected evidence and obtain one approval before code is written.

**Scope:** This task accepts raw input, an existing Work Item, or Agile Review Findings; inspects the repository before asking questions; chooses either a compact run-state contract for a truly trivial change or one `<Subject> - Agile Work Item` as durable authority; and resolves Work Item and Delivery Record placement once. It must not treat Review Findings as a complete execution contract, write production code, list folder contents, start another pipeline, push, tag, or merge.

**Verification / Definition of Done:**
- [ ] Raw input, an existing Work Item, or Agile Review Findings was accepted without rejecting its shape.
- [ ] Repository files, manifests, tests, and local conventions relevant to the request were inspected before any question was asked.
- [ ] A bounded low-risk typo, copy, simple configuration, or one-line fix with clear intent and no material decision or risk used the trivial fast path without requiring a Work Item or its template; Delivery Record placement was still resolved for later workspace use.
- [ ] Every other change used `<Subject> - Agile Work Item` containing outcome, acceptance criteria, boundary, and verification; exclusions, defect evidence, risks, decisions, and assumptions appear only when material.
- [ ] Review Findings, when supplied, produced or updated one Work Item rather than serving as the execution contract.
- [ ] Work Item and Delivery Record each have a separate exact identity/reference, create/update disposition, valid `folderId`, informational `folderPath`, and advisory; existing artifacts keep different folders when applicable, while two new artifacts normally share one valid destination.
- [ ] No new artifact destination is inside a protected imported collection; protected override, source, and counterpart candidates were skipped for a valid feature `Work` or standalone fallback with one advisory.
- [ ] Database, schema, or data-migration work explicitly records its rollback or recovery safeguards and verification implications; the category alone did not block execution.
- [ ] Relevant project-guide direction was resolved for durable work touching a guide-covered concern; trivial fast-path work did not load the guide.
- [ ] needs_input was used only for one unresolved consequential decision, which was persisted in the Work Item and was not raised again after resolution.
- [ ] One concise approval preview was shown after inspection and acknowledged; a trivial bounded change used three lines when no material decision or risk existed.
- [ ] The named Persisted handoff block stores the complete contract and separate Work Item and Delivery Record placement records for a fresh Build and Record context.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including explicitly supplied artifact ids or references, an explicitly supplied feature-level source, and a destination-folder override for artifacts that will be created. Raw requests, tickets, diffs, notes, existing Work Items, and documents titled `<Subject> - Agile Review Findings` are valid inputs. Map a bounded amendment to Work Item mode `change`, unintended behavior to `defect`, and loose engineering evidence to `task`. Review Findings identify remediation work but are not a complete execution contract.
3. Infer the subject and classify contract mode. Use `trivial-fast-path` only for a bounded low-risk typo, copy, simple configuration, or one-line fix with clear intent, one or a few deterministic criteria, an exact narrow repository-observed permitted path boundary and check, and no material decision, ambiguity, risk, or need to resume across runs. Any nontrivial, risky, ambiguous, or cross-run-resumable work uses `durable-work-item`. Do not classify by file count alone.
4. Before asking anything, inspect the supplied evidence and the relevant repository code, manifests, tests, configuration, and local conventions. Use that evidence to identify current behavior, likely affected areas, repository-native checks, and reversible implementation defaults. In durable mode, when scoped work touches code structure, UI, styling, state, API, persistence, diagnostics, or test conventions, resolve a supplied project-guide id first or make an exact-title lookup for `Project Development Guide` outside imported-collection ancestry; if none exists, use imported `agile-sdlc-project-development-guide`. If several project-owned guides match, include identity selection in the existing approval gate; do not browse folders. Use the guide's compact applicability index to read only applicable keyed concern sections and their keyed Adoption fields; do not read the Standards parent or omitted concern bodies. Approved project sections govern; Draft sections supply a forward-looking default evaluated against repository evidence. Keep guidance inside the proposed change boundary and record a material target, exception, or gradual transition in the Work Item. If neither guide is available, proceed from repository evidence with one advisory. Do not load a guide for the trivial fast path or add a decision gate solely because a section is Draft.
5. Resolve `<Subject> - Agile Work Item` when durable mode applies and `<Subject> - Agile Delivery Record` in every mode without browsing folders. Use a supplied durable artifact id first, otherwise an exact title or explicit reference. For one existing match, read its cheap folder property and preserve its current `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location; never relocate it. If several exact matches exist, include one identity selection in the approval gate. Ignore an override assigned to an existing artifact and record an advisory on that artifact's placement.
6. Resolve each create placement once. Candidate order is: a create-only override assigned to that artifact; a valid exact counterpart folder; for the Delivery Record, its valid governing Work Item folder; an explicitly supplied feature-level source's valid `Work` child; then `Project Work/Work/<Subject>`. Before accepting any candidate, determine protected imported-collection ancestry from imported-resource metadata and the cheaply fetched folder hierarchy, never a folder name. Skip every protected candidate—including an existing counterpart or governing Work Item in the imported tree—and continue in order, recording one advisory on the affected placement. Ensure only known paths, apply only host-required subject sanitization, and never list folder contents. When both artifacts are new, use the same first valid destination unless artifact-specific overrides explicitly establish different valid destinations; when both exist, preserve both folders.
7. Persist one placement record per artifact: exact artifact id/reference when present, produced title, `create` or `update` disposition, canonical `folderId`, informational `folderPath`, and one advisory when applicable. Treat `folderId` as create authority and `folderPath` as the exact recovery path if that id later vanishes. Prefer source ids, then exact references, and ask only for ambiguous identity. Do not assume workspace configuration or create a placement enum.
8. For `durable-work-item`, update the exact existing Work Item in place or create it from Agile Work Item Template (slug `agile-sdlc-work-item-template`) using its resolved `folderId`. If its template or document workspace is unavailable, report blocked and name what is unavailable. Record intended outcome, verifiable acceptance criteria, repository boundary, and verification approach; add optional detail only when material.
9. For `trivial-fast-path`, do not create, resolve, or require a Work Item or its template. Still resolve the Delivery Record identity and placement under steps 5–7; the SpecX document workspace is required when that record is created or updated. Prepare one compact execution contract in run state containing the originating request or durable reference, exact subject, observable outcome, deterministic criteria, exact permitted repository-relative paths, repository-native verification command or concrete observation, and status `approved`. If any field cannot be established exactly, use `durable-work-item`.
10. Give provenance exactly `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions. Do not turn routine inspected facts into a four-bucket recital. Use `agent-inferred` only for a reversible default supported by repository patterns. Do not silently invent product behavior, policy, destructive-data handling, compatibility behavior, or weaker verification.
11. Treat database, schema, or data-migration work, authentication or authorization or personal-data work, and published-contract changes as risk signals. Such work cannot use the trivial fast path. Describe the concrete risk, established safeguards, and verification implications in the Work Item and preview. For database, schema, or data migrations, explicitly record the repository-evidenced rollback or recovery path, data-preservation safeguards, and how recovery will be verified. The category alone is not a reason to stop or create another artifact.
12. Report needs_input only when one concrete consequential decision remains unresolved. Persist it in the Work Item; unresolved work cannot use the fast path. On a rerun, inspect the recorded resolution and do not stop on that decision again.
13. When no unresolved consequential decision remains, present one approval preview and wait for one acknowledgement. The trivial fast path uses exactly three concise lines: outcome and criteria; exact permitted paths; verification, appending its Delivery Record create/update destination and any placement advisory without adding a line. Otherwise use at most six lines covering outcome/criteria, boundary/exclusions, verification, material risks or decisions including a guide-based exception when relevant, Work Item and Delivery Record create/update destinations and any placement advisory, and next action. Do not include empty categories or re-ask approved choices.
14. After acknowledgement, approve the selected contract. For durable mode, set the Work Item status to Approved. **Persisted handoff:** store status `approved`, exact subject, contract mode, a separate Work Item placement record when applicable, a separate Delivery Record placement record, either the exact Work Item title for `durable-work-item` or the complete compact execution contract from step 9 for `trivial-fast-path`, the governing feature-source id/reference when applicable, and concise guide basis when used: exact guide id/reference, applicable section keys and statuses, and the chosen target or exception. Each placement record contains the fields from step 7 even when the two destinations match. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` are caller-variable hints, not internal state, and remain empty.
15. The compact contract exists only in this pipeline run. If a fast-path run is interrupted before the Delivery Record is written, cross-run recovery is not promised and intake may need to be rerun. Do not imply a hidden workspace or durable checkpoint.
16. Do not write production code in this task.
