**Goal:** Establish the smallest complete execution contract from inspected evidence and obtain one approval before code is written.

**Scope:** This task accepts raw input, an existing Work Item, or Agile Review Findings; inspects the repository before asking questions; and chooses either a compact run-state contract for a truly trivial change or one `<Subject> - Agile Work Item` as durable authority. It must not treat Review Findings as a complete execution contract, write production code, start another pipeline, push, tag, or merge.

**Verification / Definition of Done:**
- [ ] Raw input, an existing Work Item, or Agile Review Findings was accepted without rejecting its shape.
- [ ] Repository files, manifests, tests, and local conventions relevant to the request were inspected before any question was asked.
- [ ] A bounded low-risk typo, copy, simple configuration, or one-line fix with clear intent and no material decision or risk used the trivial fast path without requiring a Work Item, template, or document workspace.
- [ ] Every other change used `<Subject> - Agile Work Item` containing outcome, acceptance criteria, boundary, and verification; exclusions, defect evidence, risks, decisions, and assumptions appear only when material.
- [ ] Review Findings, when supplied, produced or updated one Work Item rather than serving as the execution contract.
- [ ] Database, schema, or data-migration work explicitly records its rollback or recovery safeguards and verification implications; the category alone did not block execution.
- [ ] needs_input was used only for one unresolved consequential decision, which was persisted in the Work Item and was not raised again after resolution.
- [ ] One concise approval preview was shown after inspection and acknowledged; a trivial bounded change used three lines when no material decision or risk existed.
- [ ] The named Persisted handoff block was stored completely: status = approved, subject, contract mode, and either the exact Work Item title or the compact execution contract.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given. Raw requests, tickets, diffs, notes, existing Work Items, and documents titled `<Subject> - Agile Review Findings` are valid inputs. Map a bounded amendment to Work Item mode `change`, unintended behavior to `defect`, and loose engineering evidence to `task`. Review Findings identify remediation work but are not a complete execution contract.
3. Infer the subject and classify contract mode. Use `trivial-fast-path` only for a bounded low-risk typo, copy, simple configuration, or one-line fix with clear intent, one or a few deterministic criteria, an exact narrow repository-observed permitted path boundary and check, and no material decision, ambiguity, risk, or need to resume across runs. Any nontrivial, risky, ambiguous, or cross-run-resumable work uses `durable-work-item`. Do not classify by file count alone.
4. Before asking anything, inspect the supplied evidence and the relevant repository code, manifests, tests, configuration, and local conventions. Use that evidence to identify current behavior, likely affected areas, repository-native checks, and reversible implementation defaults.
5. For `durable-work-item`, locate `<Subject> - Agile Work Item`; update it in place or create it from Agile Work Item Template (slug `agile-sdlc-work-item-template`). If its template or document workspace is unavailable, report blocked and name what is unavailable. Record intended outcome, verifiable acceptance criteria, repository boundary, and verification approach; add optional detail only when material.
6. For `trivial-fast-path`, do not create, resolve, or require a Work Item, its template, or a document workspace. Prepare one compact execution contract in run state containing the originating request or durable reference, exact subject, observable outcome, deterministic criteria, exact permitted repository-relative paths, repository-native verification command or concrete observation, and status `approved`. If any field cannot be established exactly, use `durable-work-item`.
7. Give provenance exactly `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions. Do not turn routine inspected facts into a four-bucket recital. Use `agent-inferred` only for a reversible default supported by repository patterns. Do not silently invent product behavior, policy, destructive-data handling, compatibility behavior, or weaker verification.
8. Treat database, schema, or data-migration work, authentication or authorization or personal-data work, and published-contract changes as risk signals. Such work cannot use the trivial fast path. Describe the concrete risk, established safeguards, and verification implications in the Work Item and preview. For database, schema, or data migrations, explicitly record the repository-evidenced rollback or recovery path, data-preservation safeguards, and how recovery will be verified. The category alone is not a reason to stop or create another artifact.
9. Report needs_input only when one concrete consequential decision remains unresolved. Persist it in the Work Item; unresolved work cannot use the fast path. On a rerun, inspect the recorded resolution and do not stop on that decision again.
10. When no unresolved consequential decision remains, present one approval preview and wait for one acknowledgement. The trivial fast path uses exactly three concise lines: outcome and criteria; exact permitted paths; verification. Otherwise use at most six lines covering outcome/criteria, boundary/exclusions, verification, material risks or decisions with provenance, artifact title, and next action. Do not include empty categories or re-ask approved choices.
11. After acknowledgement, approve the selected contract. For durable mode, set the Work Item status to Approved. **Persisted handoff:** store status `approved`, exact subject, contract mode, and either the exact Work Item title for `durable-work-item` or the complete compact execution contract from step 6 for `trivial-fast-path`. This is the complete Task 1-to-Task 2 state; `inputVarDefinitions` are caller-variable hints, not internal state, and remain empty.
12. The compact contract exists only in this pipeline run. If a fast-path run is interrupted before the Delivery Record is written, cross-run recovery is not promised and intake may need to be rerun. Do not imply a hidden workspace or durable checkpoint.
13. Do not write production code in this task.
