**Goal:** Load the persisted implementation result and resolved Delivery Record destination, record any established revision and evidence, set implementation completion, and hand off in at most five lines.

**Scope:** This task loads the approved contract, the separate Delivery Record placement record, and the structured implementation result; writes the Delivery Record, records evidence, and sets the implementation outcome. It must not recompute placement, relocate an artifact, rerun checks, rely on conversation, invent evidence, edit prior events, set an optional pipeline's outcome, or paste raw logs.

**Verification / Definition of Done:**
- [ ] Approved status, contract, separate Work Item and Delivery Record placement records, and the complete structured implementation result were loaded.
- [ ] The Delivery Record was updated by id in its current folder or created at its persisted destination from Agile Delivery Record Template (slug `agile-sdlc-delivery-record-template`); a vanished create-folder id re-ensured only the persisted path.
- [ ] When the result contained a Target Revision, it satisfied its persisted manifest semantics before being stored and referenced by new source `implement` events; an early blocked or needs_input result with no manifest or events did not invent them.
- [ ] The concise Implementation Summary states only established outcome, changed areas, acceptance result, and limitations or next action, citing event ids when evidence exists and otherwise citing the durable Work Item decision or Originating Request for an early blocked or needs_input outcome.
- [ ] Material decisions shipped were appended without rewriting earlier entries; a needs_input outcome names its durable Work Item decision rather than mislabeling it as shipped; and prior events remained unchanged.
- [ ] Implementation Outcome is exactly done, failed, needs_input, or blocked with a one-line reason; no other pipeline outcome was written.
- [ ] No check was rerun and no evidence was reconstructed from conversation.
- [ ] No push, tag, or merge occurred, and the handoff is at most five lines.

**Instructions:**

1. Expose concise state while working: `recording` or `blocked` when required durable state or the document workspace is unavailable.
2. Load status, subject, contract mode, separate Work Item and Delivery Record placement records, originating request when applicable, and the structured implementation result from this run. Require outcome/reason and every field implied by work actually performed: changed areas/files, per-criterion results, Target Revision manifest and revision id, target branch, limitations/next action, decision reference, and ordered verification/manual-observation entries. An early blocked or needs_input result before checks may omit the manifest, revision id, and entries. Name every conditionally required missing field and stop `blocked`; stop unless status is approved.
3. Use these outcomes: `done` means required verification passed or was concretely observed; `failed` means verification ran and found a defect or unmet criterion; `needs_input` means one unresolved consequential decision requires a person; `blocked` means the environment, authority, or required state is unavailable.
4. In durable mode, reread the Work Item by its persisted id in its current folder, advising if its display path changed; use its exact reference only when no id exists. In fast-path mode, retain the originating request and do not require or create a Work Item.
5. Load only the Delivery Record placement for this write. For `update`, reread by persisted id, write in its current folder, and advise if its path changed; never relocate or block for that move. For `create`, use the persisted `folderId`; if it vanished, re-ensure the exact persisted `folderPath` without rerunning placement, and use the replacement id. If that exact path, the template, or the SpecX document workspace is unavailable, report `blocked` and name the environmental dependency. Never list folder contents. Preserve every existing event and repeatable entry.
6. When a manifest exists, validate it under its persisted manifest semantics; boundary drift is `blocked`, unrelated outside-boundary changes are ignored, and nothing is auto-committed.
7. Append an existing manifest once as a Target Revision under Delivery Record, preserving its stable revision id. Without rerunning a check, append one Delivery Event with source `implement` for each ordered entry. Give each a new stable event id and include source, date, the revision-id reference, command or concrete action, truthful result, and concise result details. Put target branch and changed areas/files on the first relevant event and link summary claims to event ids rather than repeating details. Add criterion ids, requirement status, resolution links, artifact pointer, or limitations only when applicable. Retain failed-before-repair and passing-after-repair as separate events. An early `blocked` or `needs_input` result before checks omits all Target Revision and Delivery Event instances; never invent either.
8. Set only Implementation Outcome and Implementation Outcome Reason from the persisted result. Update the Implementation Summary near the top with only established outcome/reason, changed areas, aggregate acceptance result, and material limitations/next action. Cite new event ids when evidence exists; for an early blocked or needs_input result without events, cite the persisted Work Item decision or Originating Request instead. Accept only `done`, `failed`, `needs_input`, or `blocked`.
9. Append demonstrably shipped decisions and useful artifact links without rewriting prior entries. Do not append an unresolved consequential decision as shipped. Set Governing Work Item only in durable mode; in fast-path mode omit it and set Originating Request from the compact contract.
10. Confirm no check was rerun and no push, tag, or merge occurred.
11. Emit at most five lines labeled Outcome, Decision, Artifact, Evidence, and Next action. Artifact includes the exact Delivery Record and its informational folder path plus a persisted placement advisory only when present. Identify the stored revision id when one exists. For fast-path work, the Delivery Record is the only required durable document; if recording is interrupted before it exists, state that intake may need to be rerun because the compact contract is not cross-run recovery state. Do not initiate another pipeline.
