**Goal:** Inspect the source and repository, choose PRD or Feature mode, persist a resumable product-spec drafting contract, and obtain one approval.

**Scope:** This task accepts unformatted notes, feedback, a ticket, a user story, an initiative brief, or a product-spec excerpt; grounds it in available source and repository evidence; and confirms the mode, each produced title, and any proposed split. It must not draft the document body, modify source code, or create another artifact.

**Verification / Definition of Done:**
- [ ] Unformatted input was accepted.
- [ ] The source and relevant repository evidence were inspected before any question.
- [ ] A mode was recommended from the source and approved by the person: PRD mode for an initiative, Feature mode for a single capability.
- [ ] Source reference, subject, produced title, approved mode, and material assumptions and decisions were established.
- [ ] Provenance was recorded only for material decisions and assumptions.
- [ ] Artifact identity, a title collision, the mode recommendation, any proposed split, and any placement advisory were resolved in the same approval preview without listing folder contents.
- [ ] Existing artifacts keep their exact current folders; a new PRD uses the flat `Project Work/Initiatives` default and each new accepted Feature Spec uses its own `Project Work/Features/<approved subject>` folder, unless that artifact has a valid create-only override outside the protected imported collection.
- [ ] One preview showed only applicable provenance classes and did not force empty categories.
- [ ] The named Persisted handoff stores each exact artifact reference, canonical `folderId`, informational `folderPath`, and every other field needed by a fresh drafting context.
- [ ] Agile Product Spec Template (`agile-sdlc-product-spec-template`) was present, or the task stopped with workspace setup required and named that title and slug.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including a destination-folder override explicitly assigned to a new output as a create-only hint. Establish a durable source reference: an exact document title, ticket, commit, or supplied-input description. If no usable source exists, inspect first, then include the missing source in the single approval request.
3. Inspect the source and relevant repository files, manifests, tests, and existing specifications before asking. Infer a concise subject and identify repository-observed constraints and reversible agent-inferred defaults.
4. Recommend one mode. Use PRD mode, titled `<Subject> - Agile PRD`, when several capabilities share a product objective, users, and success measures. Use Feature mode, titled `<Subject> - Agile Feature Spec`, when one capability has significant user flows, business rules, or edge cases. Read "Agile Artifact Routing Guide" only when the source does not settle the mode or whether the default Work Item route is sufficient. The person decides; record the recommendation without creating another artifact.
5. In Feature mode, if the brief bundles independently deliverable capabilities, propose subjects and boundaries only when separate documents would clarify the work. Preserve the unsplit brief unless the proposal is approved. Do not silently impose a split. PRD mode produces one document.
6. Resolve each produced artifact's identity without browsing folders: use a supplied artifact id first, otherwise exact-title or explicit-reference lookup. For one match, read its cheap folder property and preserve its exact current `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location; defaults and overrides never move it. Ignore an override assigned to this existing artifact and include a concise advisory. If several exact matches exist, include one identity selection in the approval gate. Do not use folder-content listing to find or disambiguate artifacts.
7. Resolve placement once for each new artifact. Use a valid override explicitly assigned to that artifact. Otherwise, in PRD mode ensure and use `Project Work/Initiatives`, with the PRD directly in `Initiatives` and no per-PRD folder; in Feature mode ensure and use `Project Work/Features/<approved subject>`, applying only host-required sanitization to the approved subject. A PRD or other source folder is not inherited by a Feature Spec. Each split feature gets a separate subject folder; a general override is not silently shared across split outputs. Determine protected imported-collection ancestry from imported-resource metadata and the folder hierarchy, never a folder name. Reject a protected-tree override and use that artifact's default with one concise advisory. Fetch hierarchy only to check ancestry or ensure a known path; never list folder contents. Treat `folderId` as write authority and `folderPath` as informational. Do not assume workspace configuration or create a placement enum.
8. Check Agile Product Spec Template availability. If it is unavailable, report `blocked` and name its title and slug. Give provenance `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions. Use `unresolved` only for a consequential choice that cannot be safely inferred.
9. Present one preview of at most six lines covering source, recommended mode with each subject/title or split, intended scope, each exact update or create destination, applicable material decisions or assumptions with provenance, any collision or placement advisory, and next action. Omit inapplicable details. Set state to `waiting` and ask once for acknowledgement.
10. After acknowledgement, **Persisted handoff:** store status `approved`, source reference, approved mode, each accepted subject and produced title, split disposition, each exact artifact id/reference when one exists, collision and create/update disposition, canonical `folderId`, informational `folderPath`, any concise placement advisory, and material assumptions and decisions with provenance. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state. If the user chooses the default Work Item route, finish without approval and state that next action.
11. Do not draft the document body or modify source code.
