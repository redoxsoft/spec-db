**Goal:** Inspect the source and repository, choose PRD or Feature mode, persist a resumable product-spec drafting contract, and obtain one approval.

**Scope:** This task accepts unformatted notes, feedback, a ticket, a user story, an initiative brief, or a product-spec excerpt; grounds it in available source and repository evidence; and confirms the mode, each produced title, and any proposed split. It must not draft the document body, modify source code, or create another artifact.

**Verification / Definition of Done:**
- [ ] Unformatted input was accepted.
- [ ] The source and relevant repository evidence were inspected before any question.
- [ ] A mode was recommended from the source and approved by the person: PRD mode for an initiative, Feature mode for a single capability.
- [ ] Source reference, subject, produced title, approved mode, and material assumptions and decisions were established.
- [ ] Provenance was recorded only for material decisions and assumptions.
- [ ] Artifact identity, a title collision, the mode recommendation, any proposed split, and any placement advisory were resolved in the same approval preview without listing folder contents.
- [ ] An update (existing artifact) persists the artifact id, the current folder id, and an informational folder path, resolved during scoping by an exact title lookup across the workspace. A create (new artifact) persists only the approved folder path: `Project Work/Initiatives` for a PRD, `Project Work/Features/<approved subject>` for a feature spec, or a valid override. Nothing is created during scoping.
- [ ] One preview showed only applicable provenance classes and did not force empty categories.
- [ ] The named Persisted handoff stores, for each artifact, only the fields of its disposition — update: artifact id, current folder id, and informational folder path; create: approved folder path — and every other field needed by a fresh drafting context.
- [ ] Agile Product Spec Template (`agile-sdlc-product-spec-template`) was present, or the task stopped with workspace setup required and named that title and slug.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including a folder-path override explicitly assigned to a new output as a create-only hint. Establish a durable source reference: an exact document title, ticket, commit, or supplied-input description. If no usable source exists, inspect first, then include the missing source in the single approval request.
3. Inspect the source and relevant repository files, manifests, tests, and existing specifications before asking. Infer a concise subject and identify repository-observed constraints and reversible agent-inferred defaults.
4. Recommend one mode. Use PRD mode, titled `<Subject> - Agile PRD`, when several capabilities share a product objective, users, and success measures. Use Feature mode, titled `<Subject> - Agile Feature Spec`, when one capability has significant user flows, business rules, or edge cases. Read "Agile Artifact Routing Guide" only when the source does not settle the mode or whether the default Work Item route is sufficient. The person decides; record the recommendation without creating another artifact.
5. In Feature mode, if the brief bundles independently deliverable capabilities, propose subjects and boundaries only when separate documents would clarify the work. Preserve the unsplit brief unless the proposal is approved. Do not silently impose a split. PRD mode produces one document.
6. Resolve each produced artifact's identity without browsing folders. Look up each produced title with an exact, case-insensitive match and no folder limit, so the search covers the whole workspace. A supplied artifact id, when the person named one, must match the returned id. For one match, record an update and persist that id, its current folder id, and its folder path (empty at the workspace root). Defaults and overrides never move an existing artifact. Ignore an override assigned to this existing artifact and include a concise advisory. If several exact matches exist, include one identity selection in the approval gate. Do not list folder contents to find or disambiguate artifacts.
7. Resolve placement once for each new artifact and persist a create disposition. Store only the approved folder path, as folder names from the root, and do not create folders during scoping. Use a valid folder-path override explicitly assigned to that artifact. Otherwise, in PRD mode use `Project Work/Initiatives`, with the PRD directly in `Initiatives` and no per-PRD folder; in Feature mode use `Project Work/Features/<approved subject>`, applying only host-required sanitization to the approved subject. A PRD or other source folder is not inherited by a Feature Spec. Each split feature gets a separate subject folder; a general override is not silently shared across split outputs. Do not list folder contents. Do not assume workspace configuration or create a placement enum. Drafting creates the missing folders later, when it creates the document from that folder path.
8. Confirm the Agile Product Spec Template is available in this workspace. If it is not, report `blocked` and name its title and slug. Keep that template id for drafting. Give provenance `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions. Use `unresolved` only for a consequential choice that cannot be safely inferred.
9. Present one preview of at most six lines covering source, recommended mode with each subject/title or split, intended scope, each exact update or create destination, applicable material decisions or assumptions with provenance, any collision or placement advisory, and next action. Omit inapplicable details. Set state to `waiting` and ask once for acknowledgement.
10. After acknowledgement, **Persisted handoff:** store status `approved`, source reference, approved mode, each accepted subject and produced title, split disposition, collision and create/update disposition, the Agile Product Spec template id, any concise placement advisory, and material assumptions and decisions with provenance. For each update, store the artifact id, current folder id, and informational folder path from that exact-title lookup. For each create, store the approved folder path only. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state. If the user chooses the default Work Item route, finish without approval and state that next action. Nothing is created during scoping.
11. Do not draft the document body or modify source code.
