**Goal:** Inspect the source and repository, persist a resumable Implementation Plan drafting contract, and obtain one approval.

**Scope:** This task accepts a feature spec, a tech spec, a PRD, or unformatted notes, infers the subject and the title `<Subject> - Agile Implementation Plan`, and notes the current branch and the files the brief already names. It must not draft the plan body, modify source code, create a branch, commit, push, tag, or merge, or start another pipeline.

**Verification / Definition of Done:**
- [ ] Unformatted input was accepted.
- [ ] The source and relevant repository evidence were inspected before any question.
- [ ] Source reference, subject, title, Implementation Plan mode, delivery boundary, assumptions, and decisions were established.
- [ ] Provenance was recorded only for material decisions and assumptions.
- [ ] Artifact identity, governing feature/source identity, a title collision, and any placement advisory were resolved in the same approval preview without listing folder contents.
- [ ] An existing Implementation Plan keeps its exact current folder; a new one uses a valid create-only override, an explicitly supplied valid governing feature/source folder outside the protected import tree, or `Project Work/Work/<Subject>` with an advisory.
- [ ] One preview showed only applicable provenance classes and did not force empty categories.
- [ ] The named Persisted handoff stores the exact artifact and governing-source references, canonical `folderId`, informational `folderPath`, and every other field needed by a fresh drafting context.
- [ ] Agile Delivery Plan Template (`agile-sdlc-delivery-plan-template`) was present, or the task stopped with workspace setup required and named that title and slug.

**Instructions:**

1. Expose concise state while working: `inspecting` during discovery, `waiting` only for the single approval or one unresolved consequential decision, and `blocked` when a required workspace dependency is unavailable.
2. Accept the input as given, including an explicitly supplied primary Feature Spec or other governing feature-level source and a destination-folder override. Establish a durable source reference: an artifact id, exact document title, ticket, commit, or supplied-input description. Do not infer that every source is a placement anchor.
3. Inspect the source and relevant repository branch, commit, manifests, layout, checks, and existing technical decisions before asking. Infer a concise subject and `<Subject> - Agile Implementation Plan`; preserve acceptance criteria, decisions, and schemas only when evidenced.
4. Establish the proposed delivery boundary, dependencies, target areas, and sequencing constraints. Respect an evidenced initial slice. Resolve the produced artifact's identity without browsing folders: use a supplied artifact id first, otherwise exact-title or explicit-reference lookup. For one match, read its cheap folder property and preserve its exact current `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location; defaults and overrides never move it. Ignore a supplied override on this update and include a concise advisory. If several exact matches exist, include one identity selection in the approval gate.
5. For a new Implementation Plan, resolve placement once in this order: a valid explicit override; the folder property of the explicitly supplied primary Feature Spec or other governing feature-level source when its identity resolves and its folder is outside the protected imported collection; otherwise ensure and use `Project Work/Work/<Subject>`, applying only host-required sanitization, and record a concise standalone-placement advisory. Resolve the governing source by supplied artifact id first or exact title/reference otherwise; never use a PRD or incidental source as a feature anchor. If an override is protected, ignore it and continue to source inheritance or the default with one advisory. If the governing source is protected, use the standalone default with one advisory. Determine protection from imported-resource metadata and hierarchy ancestry, never a folder name.
6. Fetch hierarchy only to check ancestry or ensure the known fallback path; never list folder contents to find artifacts, detect collisions, or choose placement. Treat `folderId` as write authority and `folderPath` as informational. Do not assume workspace configuration or create a placement enum. If an exact artifact or governing-source lookup has several matches, resolve that identity in the single approval gate rather than disambiguating by folder.
7. Check Agile Delivery Plan Template availability; report `blocked` and name it when unavailable. Give provenance `user-stated`, `repository-observed`, `agent-inferred`, or `unresolved` only to material decisions and assumptions.
8. Present one preview of at most six lines covering source and governing anchor, subject/title and mode, delivery boundary, exact update or create destination, applicable material decisions or assumptions with provenance, any collision or placement advisory, and next action. Omit inapplicable details. Set state to `waiting` and ask once for acknowledgement.
9. After acknowledgement, **Persisted handoff:** store status `approved`, source reference, exact governing-source id/reference when supplied, subject, produced title, approved mode, delivery boundary, exact output artifact id/reference when one exists, collision and create/update disposition, canonical `folderId`, informational `folderPath`, any concise placement advisory, and material assumptions and decisions with provenance. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state.
10. Do not draft the plan body or modify source code. Do not create a branch, commit, push, tag, or merge.
