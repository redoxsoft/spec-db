**Goal:** Complete an empty boundary as not applicable, or confirm and persist a non-empty diff boundary before review.

**Scope:** This task accepts a branch, a commit range, a pull request, or a working tree diff. An empty diff completes immediately as `done` / `not-applicable` without approval or a Findings document. For a non-empty diff, it identifies exact related artifacts, resolves Review Findings placement once, and locks that boundary in one preview. It must not evaluate the diff, list folder contents, edit a file, stage, commit, push, or start another pipeline.

**Verification / Definition of Done:**
- [ ] A branch, commit range, pull request, or working tree diff was accepted.
- [ ] An empty diff completed the review run as done/not-applicable without approval or a Findings document.
- [ ] For a non-empty diff, the governing Work Item was recorded by durable id when available and exact title otherwise only when one existed, and none was invented when it did not.
- [ ] For a non-empty diff, one exact revision manifest for the reviewed boundary was resolved and persisted.
- [ ] An explicitly supplied Delivery Record title/reference was preserved first; inference occurred only when none was supplied, and any identity ambiguity was deferred to the final consolidated decision gate without creating a duplicate.
- [ ] Existing Review Findings keep their exact folder; each new Findings destination is the first valid unprotected override, Delivery Record folder, Work Item folder, feature `Work` child, or standalone default, with one advisory for skipped protected candidates.
- [ ] For a non-empty diff, artifact identity and approval used at most one consolidated preview; provenance appeared only for material assumptions or decisions and omitted empty classes.
- [ ] For a non-empty diff, the named Persisted handoff stores every field required by the evaluation task, including exact artifact references, create/update disposition, canonical `folderId`, informational `folderPath`, and any placement advisory.
- [ ] No file was edited, staged, committed, or pushed.

**Instructions:**

1. Expose concise state while working: `inspecting`, `waiting` only for the single consolidated decision gate, or `blocked` when the boundary cannot be read.
2. Accept a branch, a commit range, a pull request, or a working tree diff, plus explicitly supplied Delivery Record, Work Item, feature-level source, Review Findings, or create-only destination-folder references. Treat the exact diff boundary as the durable source reference.
3. Inspect the boundary and relevant repository context before asking. If it contains no changes, complete the review run as `done` with reason `not-applicable: the selected boundary contains no changes`; do not ask for approval, persist an approved evaluation, create or update a Findings document, or continue to the evaluation task.
4. Create the reviewed revision manifest with a stable revision id and full base commit SHA. A clean revision has no boundary entries and represents that exact commit. For a dirty revision, treat the base SHA as ancestry context and persist entries sorted by repository-relative path for every path changed or untracked inside the reviewed permitted boundary relative to that base: path plus SHA-256 of regular-file bytes, SHA-256 of symlink target bytes, `gitlink:<commit>` for a submodule, or `MISSING`. Ensure no changed path in that boundary is absent; optionally describe the boundary, do not compute an aggregate hash, and do not auto-commit.
5. Infer the subject and findings title. Resolve related artifact identities without browsing folders, using a supplied durable id first and otherwise an exact title or explicit reference. Preserve an explicitly supplied Delivery Record reference first; only when none was supplied may `<Subject> - Agile Delivery Record` be inferred. Resolve the governing Work Item only when one exists; never invent it. If an exact lookup has several matches, retain the exact candidates, inspect their cheap metadata and evidence needed for the preview, and defer identity selection to step 9; do not ask immediately or choose by folder. The Delivery Record is an optional one-way link only; Review never mutates it.
6. Resolve the Review Findings artifact by supplied id first and otherwise its exact stored title. If several exact Findings documents match, retain the exact candidates, read their cheap folder properties, and defer identity selection to step 9; do not ask immediately or create a duplicate. For each existing Findings candidate needed for the preview, preserve its exact canonical `folderId` and informational `folderPath`, even at workspace root, under the imported collection, or in an unconventional location. Ignore a supplied override on an update and include one concise advisory. Defaults, sources, and later feature context never relocate an existing artifact.
7. For new Findings, resolve placement once in this order: create-only override; exact Delivery Record folder; exact governing Work Item folder; the `Work` child of an explicitly supplied feature-level source; then `Project Work/Work/<Subject>`. Determine protected imported-collection ancestry for every candidate from imported-resource metadata and the cheap folder hierarchy, never a folder name. Skip a protected override, Delivery Record, Work Item, or feature source and continue in order; use one concise advisory for the final fallback. Thus an existing artifact in the imported tree may update there but can never colocate a new Findings document. Ensure only the selected known path, apply only host-required subject sanitization, and never list folder contents.
8. Prefer related artifact ids and read their cheap folder properties directly. Reuse an existing Work Item's exact folder even if feature context appears later only when that folder is unprotected. Treat `folderId` as create authority and `folderPath` as the exact recovery path if the id later vanishes. Do not assume workspace configuration or create a placement enum. Missing or conflicting placement evidence follows the deterministic fallback in step 7 with an advisory; placement ambiguity alone never opens a decision gate.
9. Record provenance only for material assumptions or decisions. Present one preview of at most six lines with source boundary/title, revision id, any exact artifact identity candidates, material scope facts or decisions, the candidate-dependent Findings update or deterministic create destination and any placement advisory, and next action. In one response, request any needed identity selection and approval of the resulting review scope; treat that response as the only decision gate and do not ask for approval again.
10. **Persisted handoff:** store status `approved`, explicit non-empty boundary state, source boundary description, revision id and complete manifest, exact governing Work Item id/reference when one exists, subject, findings title, exact Findings id/reference when one exists, Findings create/update disposition, canonical `folderId`, informational `folderPath`, any concise placement advisory, optional exact Delivery Record id/reference, exact feature-source id/reference when supplied, and material assumptions or decisions. This is the only placement resolution and the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state.
11. Do not evaluate or edit the diff, stage, commit, or push.
