**Goal:** Confirm implementation completed on one persisted Target Revision with no unresolved required verification failure, then define deterministic non-overlapping living-spec updates.

**Scope:** This task resolves one exact existing Delivery Record, rechecks a selected Target Revision, maps the upstream gate, and selects exact existing living specs outside the implementation boundary. It must not update living specs yet, edit source or tests, deploy, publish, merge, or start another pipeline.

**Verification / Definition of Done:**
- [ ] An explicitly supplied Delivery Record id/reference was used first; inference occurred only when none was supplied, and any identity ambiguity was deferred to the final consolidated decision gate.
- [ ] The selected revision satisfied its persisted manifest semantics.
- [ ] Upstream failed, blocked, needs_input, and missing/unreadable state mapped to failed, blocked, needs_input, and blocked respectively.
- [ ] After the gate passed, each existing living-spec target had a stable target id, exact durable artifact id/title or reference, exact repository path and section, current folder identity when applicable, and deterministic intended section change; an empty list remained a valid done no-op.
- [ ] Every proposed living-spec path was preflighted against the implementation permitted boundary before approval; overlap stopped blocked before mutation.
- [ ] After the gate passed, artifact identity, revision, targets, and approval were resolved in at most one consolidated preview; provenance appeared only for material assumptions or decisions.
- [ ] The named Persisted handoff stores every field required by Task 2.
- [ ] Application source and tests were not edited. Nothing was deployed, tagged, published, or merged.

**Instructions:**

1. Expose concise state while working: `inspecting`, `waiting` only for the single consolidated decision gate, or `blocked` when required documents are unavailable.
2. Use these outcome meanings: `done` means required verification passed or was concretely observed; `failed` means verification ran and found a defect or unmet acceptance criterion; `needs_input` means one unresolved consequential decision requires a person; `blocked` means the environment or authority is unavailable, or required durable state is unavailable.
3. Resolve an explicitly supplied Delivery Record id first, then an exact reference, and infer `<Subject> - Agile Delivery Record` only when neither was supplied. When an exact lookup has several matches, retain the exact candidates, inspect their cheap metadata and the evidence needed below, and defer identity selection to step 8; do not ask immediately. Absence is `blocked`. Persist the eventual selection's id/reference and cheap current folder property. This update-only pipeline never lists folder contents, creates a replacement, or relocates the record.
4. For each viable Delivery Record candidate needed for the final preview, inspect its revision ids and stored manifests. When several revisions are present and none was explicitly selected, retain the exact revision candidates and defer revision selection to step 8; do not ask immediately. Validate every candidate pairing needed for the preview under its persisted manifest semantics; boundary drift for the eventual selection is `blocked`, unrelated outside-boundary changes are ignored, and nothing is checked out or auto-committed.
5. For each viable candidate pairing needed for the preview, read Implementation Outcome and append-only events. Map the gate exactly: upstream `failed` -> `failed`; upstream `blocked` -> `blocked`; upstream `needs_input` -> `needs_input` and cite its durable decision; missing or unreadable outcome, manifest, event state, or contract boundary -> `blocked`. For upstream `done`, require a source `implement` event in that revision lineage and no unresolved required failed event in that lineage. A failure is resolved only by later passing required evidence in the same lineage that links to its event id; not-applicable never resolves it. Missing matching implementation evidence is `blocked`; an unresolved required verification failure is `failed`.
6. For each viable candidate pairing needed for the preview, inspect only exact existing living documents supplied directly or linked from durable artifacts for the subject. Prefer each target's durable artifact id and otherwise preserve its exact reference; never discover targets by folder listing or create a missing spec. Include a target only when matching-revision evidence supports a criterion or shipped decision. Persist its stable target id, exact identity, repository path, section, deterministic intended change, supporting id, and cheap current folder property when exposed. An empty target list is a valid done no-op.
7. Before the decision gate, preflight every candidate-dependent target living-spec repository path against the corresponding persisted implementation permitted boundary. If the eventual selection overlaps it or would invalidate its revision, stop `blocked` and name the overlapping paths. Do not edit anything.
8. Record provenance only for material assumptions or decisions. Present one preview of at most six lines with exact record candidate title and informational current folder path, revision candidate, candidate-dependent gate evidence and exact target actions, material decisions, and next action. In one response, request any needed artifact or revision selection and approval of the resulting target plan; treat that response as the only decision gate and do not ask for approval again.
9. **Persisted handoff:** store status `approved`, exact source Delivery Record durable id when available and exact title/reference, canonical current `folderId`, informational `folderPath`, subject, selected revision id and complete manifest, exact implementation permitted boundary, gate evidence, and target entries with stable target ids, exact durable artifact ids when available plus exact titles or references, repository paths, existing sections, canonical current `folderId` and informational `folderPath` when available, deterministic intended section changes, and supporting ids, plus material assumptions or decisions. This is the complete Task 1-to-Task 2 state; `inputVarDefinitions` remain empty because they are caller hints, not internal state.
10. Do not mutate documents or the repository.
