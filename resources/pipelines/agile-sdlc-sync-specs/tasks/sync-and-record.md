**Goal:** Apply deterministic non-overlapping living-spec updates one target at a time, recording each target immediately and resuming safely after interruption.

**Scope:** This task updates only the approved existing sections for criteria met and decisions shipped, persisting per-target progress before mutation and appending a separate sync event immediately after each target update. It is deterministic and resumable, not transactional. It must not edit application source or tests, invent a history section, delete prior evidence, overwrite deferred scope or unresolved questions, deploy, tag, publish, merge, or continue when this run is not approved.

**Verification / Definition of Done:**
- [ ] Status was loaded from SpecX run context for this run, and the task stopped unless it was approved.
- [ ] The exact persisted Delivery Record title was reread and the implementation outcome, matching-revision event, and required verification history were reevaluated before editing.
- [ ] Upstream failed, blocked, needs_input, and missing/unreadable state mapped without collapsing outcomes.
- [ ] All target paths were preflighted against the implementation permitted boundary before the first edit; overlap stopped blocked without mutation.
- [ ] Updates were limited to criteria the record shows were met and decisions the record shows shipped.
- [ ] Per-target progress was persisted before mutation; targets were processed one at a time, and each completed update gained its own append-only sync event immediately.
- [ ] Resume reconciliation compared the intended section change, actual target, and existing event without repeating a completed edit or event; ambiguous or mismatched partial state blocked and named the target.
- [ ] Actual existing target sections were updated in place; prior evidence was preserved, and deferred scope and unresolved questions were not overwritten.
- [ ] An empty living-spec list completed as a done no-op and appended one no-op sync event.
- [ ] Application source and tests were not edited. Nothing was deployed, tagged, published, or merged. No other pipeline was started.
- [ ] The handoff is at most five lines: outcome, decision needed, document written, evidence, and next action.

**Instructions:**

1. Expose concise state while working: `synchronizing`, `recording`, `waiting` for one unresolved consequential decision, or `blocked` when an approved document or required durable state is unavailable.
2. Reload the Task 1 **Persisted handoff**: approved status, exact source Delivery Record title, subject, selected revision id and complete manifest, exact implementation permitted boundary, gate evidence, target entries with stable target ids, exact titles and paths, existing sections, deterministic intended section changes, and supporting ids, plus material assumptions or decisions. Name every missing field and stop `blocked`; do not infer replacement state from conversation. Stop unless status is approved.
3. Use these outcome meanings: `done` means required verification passed or was concretely observed; `failed` means verification ran and found a defect or unmet acceptance criterion; `needs_input` means one unresolved consequential decision requires a person; `blocked` means the environment or authority is unavailable, or required durable state is unavailable.
4. Before any edit, validate the selected revision under its persisted manifest semantics; boundary drift is `blocked`, unrelated outside-boundary changes are ignored, and nothing is checked out or auto-committed.
5. Re-read the exact stored Delivery Record and reapply the gate before editing. Map upstream `failed` to `failed`, `blocked` to `blocked`, and `needs_input` to `needs_input` citing its durable decision; missing or unreadable record, outcome, manifest, event state, or boundary is `blocked`. For `done`, require a source `implement` event in the selected revision lineage. A required failure is resolved only by later passing required evidence in that lineage that links to it; not-applicable does not resolve it. An unresolved required failure is `failed`.
6. Preflight every persisted target path again against the implementation permitted boundary before the first mutation. If any path overlaps or would invalidate the manifest, stop `blocked` and name it. Do not perform a post-edit implementation-manifest comparison: approved living-spec edits are expected outside the implementation boundary.
7. Use the selected revision id as the evidence revision id by default. If the selected manifest is dirty and current HEAD is a descendant commit containing exactly its manifested boundary state with no uncommitted boundary drift, this optional pipeline may append a new clean manifest for the current full SHA with a new revision id and `Derived From Revision ID` pointing to the selected dirty revision. Persist the evidence revision id before target processing; on resume reuse an existing exact bridge instead of duplicating it, and never overwrite the original dirty manifest.
8. Process targets in persisted order, one at a time. Before mutating a target, persist its progress entry with target id, title, path, section, prior section state, deterministic intended section change, supporting ids, evidence revision id, and state `pending`. On every start or resume, compare that intended change with the actual target and a matching source `sync` event: if both update and event exist and agree, mark complete without repeating either; if the complete update exists but its event is absent, append the missing truthful event immediately and mark complete; if neither exists and the prior state still matches, apply only that section change, append its separate event immediately, then mark complete. If the event exists without the intended update, the target differs from both known states, or any partial state is mismatched or ambiguous, stop `blocked` and name the target. Each event uses a new event id, source, date, the evidence revision id, target id/title/section and concrete action, result, result details, and applicable supporting criteria or decisions. Preserve document structure, prior evidence, deferred scope, unresolved questions, the implementation outcome, Implementation Summary, manifests, and earlier events.
9. If the persisted target list is empty, append exactly one source `sync` no-op event referencing the evidence revision id with a concise reason; on resume reuse an existing matching no-op event and do not append another.
10. Emit at most five lines labeled Outcome, Decision, Artifact, Evidence, and Next action, identifying the evidence revision id. Do not deploy, tag, publish, or merge.
